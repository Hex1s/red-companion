## Общая картина

**Сервер** как код готов: контракт, подпись манифеста, загрузка релизов, админка, деплой-скрипты есть, авторизация админки последовательна. Но он **ни разу не стоял на VPS**, тегов в репозиториях нет, `deploy.yml` и `release.yml` ни разу не срабатывали.

**Клиент** к серверу не подключён вообще: в `src-tauri/Cargo.toml` нет `reqwest`/`tauri-plugin-updater`, `capabilities/default.json` — только `core:default` и `opener:default`, `tauri.conf.json` без `plugins.updater`, ни одной сетевой команды. Нет `LICENSE`, `README.md` — шаблон Tauri, версия `0.1.0`, `CHANGELOG.md` с единственным «Первая сборка».

**Главные риски, по убыванию:**

1. **Updater — дверь в одну сторону.** Версия, ушедшая без рабочего updater с верным `pubkey`, остаётся «базой без обновлений». Проверить его можно только на *паре* версий (`0.9.0 → 0.9.1`) с настоящими подписями на настоящем VPS.
2. **Данные мастера + updater сходятся в одной точке.** Первое же обновление через updater (1.0.1, скорее всего с миграцией V6) запустит `refinery` на живой базе без копии, без WAL, без диалога при ошибке: `Storage::open(...)?` в `setup` (`lib.rs:1989`) при сбое закрывает приложение без окна. Этот риск в аудитах стоял как «важный»; в связке с автообновлением я поднимаю его до блокера.
3. **Конвейеры релизов написаны «вслепую».** Первая сборка macOS, первая подпись minisign реальным файлом, первая загрузка >100 МБ через nginx произойдут на теге.
4. **Объём 1.0.0 противоречит сам себе.** По решениям владельца (в аудите SRV): Windows + macOS + Android, синхронизация справочников — в 1.1. Но Android в ROADMAP — это 8.1, 8.2, 8.3, 8.6, все `[ ]` (адаптив, файлы, сборка, обновление APK): самый большой по объёму и риску кусок, при этом он никак не нужен для автообновления Windows/macOS. Конвейер уже умеет выпускать без него (`ANDROID_ENABLED`), поэтому его стоит развязать от тега `v1.0.0` (см. «Рекомендуемый порядок»).
5. **Юридическое** (лицензия R. Talsorian для данных по книге, публичность репозитория) — решение владельца, технически не закрывается.

**Готовность (моя оценка):** сервер ~80 % кода / 0 % операционно; клиент ~0 % интеграции, механики и UI готовы. Реалистичный критический путь — клиентский updater + репетиция на VPS, а не серверные правки (они на 1–2 дня).

## Новые проблемы

Найдено при совместном чтении (в исходных аудитах нет или недооценено).

**N1. Два документа не согласованы по объёму клиента 1.0, а решения владельца делают регистрацию ненужной для updater.** Аудит APP требует в 1.0 регистрацию + проверку манифеста (P0-3, размер L), аудит SRV пишет «регистрация и манифест, если в 1.0». При этом решены Q2 (updater анонимный) и Q3 (синхронизация справочников в 1.1). Токен нужен только для `/manifest`, `/about`, `/app/changelog`, `/packs`, `/collections` (`app.ts:65,81`, `v1.ts`). Значит **минимальный 1.0 — это updater + «О приложении» с вшитым запасным текстом**, а регистрация и проверка манифеста уезжают в 1.1 вместе с `ApiDataSource` и не блокируют тег. Последствие, которое надо принять осознанно: без проверки манифеста в 1.0 **нельзя принудительно потребовать обновление** (`min_supported` живёт только в манифесте). Решение — вопрос Q-A.

**N2. `/about` и `/app/changelog` тоже требуют токена** (`app.ts:65` и `:81`), хотя «анонимным» предлагается сделать только `/app/update`. Если регистрация не прошла (429, нет сети), экран «О приложении» и «Что нового» останутся пустыми, и вшитый запасной текст не спасёт список изменений новой версии. Ничего секретного в них нет (changelog и так показывается на публичном сайте). → сделать анонимными вместе с `/app/update` (тот же лимит по хэшу IP).

**N3. Миграция БД и автообновление образуют неявный блокер.** Аудиты разносят «защиту БД» (APP I1) и «updater» (B2). Но порядок событий: пользователь на 1.0.0 получает 1.0.1 через updater → новый бинарник сразу запускает `refinery` на его живой базе → ошибка миграции = окно не открывается (`Storage::open(...)?` в `setup`, `panic = "abort"` для паник). Откатиться некуда: updater даёт только `version > current` (`findUpdate`, `releases.ts:170`), а «Отозвать» ничего не откатывает. Поэтому копия БД перед миграцией и диалог ошибки — **до 1.0.0**, не после. Дополнительно **проверить**: поведение `refinery` при «в базе применена миграция, которой нет в бинарнике» (старый установщик поверх нового) — по умолчанию abort, пользователь без окна.

**N4. Ключ подписи манифеста вшивается в клиент без идентификатора и без ротации.** Аудит APP разбирает ротацию ключа updater (B2), но не ключа манифеста; аудит SRV хранит публичный ключ как константу (`/PiKqf…=`). Один вшитый ключ → потеря/компрометация = клиенты 1.x не принимают манифест. Закладывать до 1.0, пока формат манифеста не зафиксирован: `key_id` в манифесте и список допустимых ключей в клиенте. Если проверка манифеста уезжает в 1.1, то это окно в 1.0 «бесплатное», но тогда ключ нужно вшить во 1.1 из расчёта на ротацию.

**N5. Пре-релизные теги ломают конвейер в конце, а не в начале.** `release.yml` срабатывает на `v*.*.*`, т.е. и на `v1.0.0-rc.1`; job `check` сверит версию с `tauri.conf.json` (пройдёт, если там `1.0.0-rc.1`), затем всё соберётся, а `upload-release.mjs` отвергнет версию (`/^\d+\.\d+\.\d+$/`) и сервер тоже (`semver.ts` — «no pre-releases»). Три платформы будут собраны зря. → Ограничить паттерн тега и проверять формат в `check` (то же для `deploy.yml`, п.20).

**N6. В `release.yml` нет `workflow_dispatch`, `fail-fast: true`.** Единственный способ проверить сборку macOS (включая C-зависимость `webp`/libwebp для `x86_64` на ARM-раннере `macos-latest`) — пушить тег. Падение одной macOS-сборки отменяет остальные и срывает `publish`. Нужны ручной запуск без публикации и `fail-fast: false` хотя бы на репетиции. (Q11 аудита SRV, но с акцентом на `fail-fast`.) Кросс-сборка `webp` под `x86_64-apple-darwin` на ARM — **проверить**, это неочевидный риск.

**N7. Пароль ключа Android: `apksigner` вызывается только с `--ks-pass`.** Подтверждено (`release.yml:134-135`). Дополнительно: ни один из аудитов не отметил, что `ANDROID_KEY_ALIAS` в секретах есть, а пароля ключа (`--key-pass`) нет. Если пароль ключа ≠ пароль хранилища — подпись падает на теге.

**N8. Три независимые «пороговые» сущности без единой семантики.** `content.min_app_version` (в манифесте контента), `app.min_supported` (в блоке `app`), и `AppRelease.minContentSchema/maxContentSchema` (в БД, CI их не шлёт). Аудит SRV называет первые две (C-2), но не связывает с третьей: у клиента нет ни одной константы «максимальная понимаемая схема», поэтому поля серверу ничего не дают. Для 1.0 достаточно записать в контракте: «`app.min_supported` — единственный порог принудительного обновления; остальные не используются до 1.1».

**N9. Подпись манифеста считается дважды разными способами, и вектор должен покрывать оба.** Без релиза приложения (`!app`) отдаётся сохранённая подпись манифеста *без* `app`, с релизом — подпись пересчитывается на каждый запрос над `{…manifest, app}` (`v1.ts:76-79`). Клиент проверяет подпись над «всем кроме `signature`» в обоих случаях, но набор векторов (`manifest-vectors.json`) должен содержать оба варианта, иначе первый реальный отказ случится на пользователе в день первого релиза приложения.

**N10. Подпись установщика Windows и SmartScreen — не там, где ждут.** Установка *через updater* не получает Mark-of-the-Web (скачивает само приложение), поэтому SmartScreen поражает только первую установку с сайта. Это снижает срочность платной подписи Windows для самого `1.0.0` (первое обновление дойдёт без предупреждения), но не для первых пользователей. Проверить на чистой Windows при репетиции.

**N11. Анонимный updater теряет учёт версий.** Сейчас `Installation.appVersion` обновляется только в `authenticate` (`auth.ts:23-30`). Когда updater станет анонимным, единственная статистика «кто на какой версии» пропадёт. Аудит SRV отмечает это (C-10), но не предлагает замену: самое простое — счётчик по `X-App-Version` в `rate_limit`-подобной таблице (без хранения IP) или агрегат в `DownloadEvent`.

**N12. Разные политики версий серверного тега и приложения.** Оба репозитория слушают тег `v*.*.*`, но смысл разный: тег сервера = образ + деплой (`package.json` сервера остаётся `0.1.0`), тег приложения = релиз для пользователей. Тег `v1.0.0` в обоих репо создаёт путаницу при разборе инцидентов («сервер 1.0.0» ≠ «приложение 1.0.0»). Решить схему заранее (например, сервер `s1.0.0`/`0.x`) — вопрос Q-F.

**N13. Доверие к `url` в ответе updater держится на подписи, а не на TLS.** `url = publicOrigin() + /releases/...` (`app.ts:56`). При ошибочном `BETTER_AUTH_URL` клиент получит неработающую ссылку (доступность), но подменить установщик нельзя — Tauri проверяет minisign по вшитому `pubkey`. То есть п.14 — про доступность, а настоящий корень доверия — ключ updater (N4, B2).

**N14. Единственный `isVersion` без пре-релизов также блокирует формат `current_version` у приложения.** `getAppUpdate` вернёт 400, если версия приложения содержит суффикс (`1.0.0-rc.1`), и updater у такого клиента молча не сработает. Следствие N5: пре-релизные сборки для тестеров должны иметь чистый `X.Y.Z`.

5. Тег сервера → TLS → `import-seed` → `release:publish` → админ → токен CI → тексты «О приложении» (B-5, шаги §8.11).
6. Сухая сборка macOS через `workflow_dispatch` (N6) — чтобы увидеть реальные имена `.dmg`/`.app.tar.gz` и ошибки `webp` до тега.

Фаза 3 — репетиция
7. Теги `v0.9.0`, потом `v0.9.1` в приложении. Проверки: обновление на чистой Windows и на Mac, «Отозвать», загрузка >100 МБ, minisign на настоящей `.sig`, восстановление из бэкапа. Исправления — по результатам; повторять до зелёного.
8. Очистить репетиционные следы (`DownloadEvent`, `AuditLog`, версии `0.9.x` отозвать).

Фаза 4 — подготовка 1.0.0
9. B-7 (версия, CHANGELOG, метаданные, LICENSE/README, пометка «неофициальный материал»), I-4 (CI), I-5 (CSP, окно).
10. Если Q-A = «манифест в 1.0»: I-1 (векторы, `issued_at`, `key_id`) → клиент: `register_installation`, `fetch_manifest`, проверка подписи, монотонность. Иначе перенести на 1.1.
11. Если Q-B = «Android в 1.0»: I-6 — **отдельным треком**, не блокирующим тег (см. ниже).

Фаза 5 — выпуск
12. Тег `v1.0.0` (приложение). Проверка: сайт показывает версию, `GET /api/v1/download/windows` отдаёт установщик, обновление с `0.9.1` проходит. Затем: напомнить себе, что **первый хотфикс (`1.0.1`) — первая настоящая проверка миграции через updater**.

*Порядок «сервер → клиент» важен в трёх местах:* B-2 до репетиции (иначе updater на репетиции упрётся в 401); I-1 — сервер генерирует векторы, потом клиент тестирует; Android-блок `app.android` — сервер уже готов, клиент потребителем.
