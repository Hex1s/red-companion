# Памятка: релиз сломан, выпускаем хотфикс

Откатить версию приложения у пользователей нельзя: updater отдаёт только версию выше текущей. Поэтому ошибку исправляют **новой** версией (`1.0.1`, `1.0.2` ...). «Отозвать» в админке лишь прячет релиз: новые установки и обновления его больше не получают, а те, кто уже обновился, остаются на нём.

## 1. Оценить
- Какая версия сломана и у кого (Windows, macOS, Android).
- Задеты ли данные? Приложение не открывает базу, а показывает диалог: файл при этом не тронут, копия перед миграцией лежит рядом.
- Где логи пользователя: `%LOCALAPPDATA%\app.red-companion\logs\red-companion.log`. Данные: `%APPDATA%\app.red-companion\red-companion.db`, копии: папка `backups` там же.

## 2. Остановить расползание
В админке сервера: «Релизы приложения» → у сломанной версии **«Отозвать»**. Проверка: `GET /api/v1/app/update/windows/x86_64/<предыдущая версия>` отвечает `204`.

## 3. Выпустить исправление
1. Исправить, прогнать `cargo test --workspace` и `npm run check`.
2. `npm run version:set -- X.Y.Z` (следующий номер, не уже использованный), заполнить раздел в `CHANGELOG.md` (`ru` и `en`, без `TODO`).
3. Коммит, `git tag vX.Y.Z`, `git push origin main vX.Y.Z`.
4. Дождаться зелёного релиза (все платформы), в админке нажать **«Опубликовать»**. Без этого CI только завершает черновик.
5. Проверить: на машине со сломанной версией «Проверить обновления» находит исправление, данные на месте.

## 4. Если сломана миграция базы
- Пользователь не теряет данные: перед миграцией приложение копирует базу в `backups/pre-migration-*` (хранится 5 последних), а при ошибке показывает диалог с путями.
- Исправление выпускается новой версией. Если надо вернуть данные: закрыть приложение, заменить `red-companion.db` нужной копией.
- Миграции только растут: нельзя править уже выпущенный файл миграции (изменится контрольная сумма, и база пользователей перестанет открываться). Ошибку исправляют новой миграцией. Файлы `*.sql` всегда с LF (`.gitattributes`, тест в `storage`).

## 5. Если сломан контент справочников
- Клиент не принимает релиз контента с номером меньше уже принятого, поэтому вернуть старый нельзя: исправить записи в админке и опубликовать **новый** релиз контента.
- Подпись и хэши проверяются на клиенте; при несовпадении скачивание отклоняется с понятной ошибкой, данные пользователя не портятся.

## 6. Если сломан сервер
- Выкладка сервера: `ssh` на VPS, `cd /srv/red-companion && ./deploy.sh sX.Y.Z` (откат на прежний тег образа). Миграции сервера должны быть совместимы со старым образом на один релиз назад.
- Если упала миграция сервера: восстановить базу из дампа `/srv/red-companion/backups/pre-deploy-*` (и из ночного бэкапа, см. `backup.sh`).
- Состояние: `curl https://red-companion.ru/api/health` (200), `docker compose logs app --tail 100`.

## 7. Принудительное обновление
В 1.0 его нет: приложение работает локально при любой версии. Порог `RC_MIN_SUPPORTED` появится вместе с проверкой «версия устарела» (1.1).

## 8. После выпуска
- Записать, что случилось и почему, в `docs/` или в сообщение коммита.
- Если причина в процессе (не поймали тестом), добавить тест или проверку в CI.
