**Про ключи простыми словами (Q-G).** Каждое обновление подписывается приватным ключом, приложение проверяет подпись публичным, вшитым внутрь. Потеряете или скомпрометируете приватный ключ, и старые установки перестанут принимать обновления: придётся просить всех переустановить вручную. «Дружелюбный к пользователю» вариант — сразу сгенерировать **второй, резервный** ключ и вшить оба публичных: тогда основной можно заменить обычным обновлением, ничего не ломая. Приватный резервный ключ хранится отдельно и офлайн.

## Сессия 0. Решения и ключи (S, владелец)

Решения Q-A…Q-M приняты опросом (таблица выше), `.gitignore` поправлен. Остаётся то, что делает владелец руками.

- **Ключи updater (N15, Q-G):** владелец выполняет дважды `! npx tauri signer generate -w <путь вне репозитория>`: основной и резервный. Приватные ключи и пароли хранит вне репозитория (резервный — отдельно, офлайн). Публичные ключи отдаёт Claude для `tauri.conf.json`; основной кладёт в `.env` сервера (`UPDATER_PUBLIC_KEY`). **Проверить**, как серверный `UPDATER_PUBLIC_KEY` и `signed`-проверка в `releases.ts` ведут себя со вторым ключом (подписывает основной, резервный только вшит). Публичный ключ манифеста сверить с серверным.
- **Сервер (Q-F):** в серверном репо перевести `deploy.yml` и `deploy.sh` на префикс `s` (вне этого репозитория).
- **Секреты GitHub приложения:** `TAURI_SIGNING_PRIVATE_KEY` (пароль пустой по выбору владельца, секрет `…_PASSWORD` не заводится; подпись проверить на сухой сборке), `RC_CI_TOKEN` появится только после выкладки сервера (см. 5а); Android-секреты (keystore, пароль хранилища, `ANDROID_KEY_PASSWORD`, alias) понадобятся к A2.
- **Android keystore:** сгенерировать заранее и сохранить копию вне репозитория: потеря ключа APK = невозможность обновлять приложение на устройствах.
- **Результат:** решения записаны в `docs/ROADMAP.md` (раздел 0 и Phase 7/8), задачи `RP-1…RP-6` и A1–A4 добавлены с зависимостями; на 7.8 и 8.5 ссылки на этот план (Claude сделает по вашей команде).

Готово, когда: ключи выпущены и публичные у Claude; ROADMAP обновлён.

## Сессия 5. Репетиция на настоящем VPS — RP-5 (B-5, L)

Ведёт владелец; Claude участвует точечно (читает логи, чинит найденное). Это не одна сессия подряд, а серия коротких заходов по результатам каждого шага. Делится на три блока.

**5а. Сервер (владелец, `deploy-checklist.md` §4, §8).** Порядок жёсткий; первая настройка VPS один раз вручную, дальше выкладки идут по тегу.
1. DNS `red-companion.ru` → VPS; пакеты (Docker и т. д.), доступ к GHCR.
2. `.env` на VPS. Без `UPDATER_PUBLIC_KEY` (основной публичный ключ updater) и `MANIFEST_PUBLIC_KEY` сервер в production не стартует, `/api/health` = 503 (N15).
3. Секреты GitHub **серверного** репозитория для `deploy.yml` (доступ на VPS).
4. До первого тега: `deploy.yml` и `deploy.sh` серверного репо переведены на префикс `s` (Q-F).
5. Тег сервера `s1.0.0` (образ → выкладка → миграции), `/api/health` = 200.
6. TLS: сначала staging, затем боевой сертификат.
7. `bootstrap.sh` (seed, первый релиз контента, админ, CI-токен), только после того как сервер заработал.
8. **CI-токен из `bootstrap.sh` (или `npm run ci:create-token`) → секрет `RC_CI_TOKEN` в репозитории приложения.** Без него шаг `publish` не работает; сухая сборка его не использует.
9. `preflight`, cron `data:prune` (ежедневно) и `releases:cleanup` (еженедельно, сначала `--dry-run`), `nginx -t`, бэкап и проверка восстановления.

**5б. Сухая сборка.** `workflow_dispatch` из сессии 2: увидеть реальные имена `.dmg` и `.app.tar.gz`, ошибки `webp` на `x86_64-apple-darwin` (N6). Claude правит `release.yml` по итогам.

**5в. Пара релизов.** Теги `v0.9.0`, затем `v0.9.1` (ставятся с `ANDROID_ENABLED=true`, APK проходит те же проверки: установка на планшет, «Обновить», `sha256`); после каждого в админке «Релизы приложения» → «Опубликовать» (N16). Проверки: обновление `0.9.0 → 0.9.1` на чистой Windows (и на Mac, если в плане), «Отозвать» → обновление не предлагается, загрузка >100 МБ через nginx, minisign на настоящей `.sig`, SmartScreen на первой установке (N10). Затем очистить следы (`DownloadEvent`, `AuditLog`, отозвать `0.9.x`).

Готово, когда: чек-лист §10 из аудита сервера проходит целиком, найденные ошибки исправлены и повторно проверены. Если репетиция выявила правки в клиенте, это отдельные короткие сессии, а не расширение этой.
