# План вычитки книги и разделения «ядро / сервер»

Цель: до перехода к серверной части (фаза 7) вынести в приложение **все правила, без которых ничего не работает**, и сделать их доступными в справочнике, в том числе подсказками при наведении (описание навыка, приёмы стиля). Одновременно решить, что зашить в приложение, а что получать с сервера.

Связанные документы: `docs/ROADMAP.md` (задача 2.11), `docs/GLOSSARY.md` (устойчивые ID терминов), `CLAUDE.md` (правила по данным из книги и лицензии).

## 1. Принципы разделения

Решение 2.0 в роадмапе остаётся основой. Здесь оно уточняется проверочными вопросами. Запись идёт **в ядро**, если на «да» отвечают на первый и хотя бы один из остальных:

1. Приложение без неё не работает или не считает правильно (формулы, пороги, состояния ранения, таблицы, на которых стоит механика)?
2. Её не расширяют дополнения (DLC) и не правит мастер?
3. Она нужна офлайн с первой минуты, до первой загрузки контента?

Запись идёт **на сервер**, если дополнения могут её добавить или изменить, или мастер захочет менять сам (оружие, броня, NPC, стили, программы, имплантаты, районы, лор).

| Слой | Что там | Как хранится | Тексты |
|---|---|---|---|
| **Ядро** (в бинарнике) | Всё, что берётся именно из основной книги правил: формулы и механика (Rust); таблицы критических травм; список навыков **с описаниями**; глоссарий; сводки правил (бой, ранения, укрытие, лечение) | `crates/rules-core/data/seed/*.json` + код | Ключи в `ru.json`/`en.json` |
| **Сервер / базовый набор** | Всё, что расширяется пакетами: оружие, броня, щиты, снаряжение, NPC, боевые стили, роли и ранги, имплантаты, препараты, программы, ЛЁД, транспорт, районы | Коллекции `DataSource`: встроенный снимок → кэш → API; **«базовый набор»** ставится мастером установки и обновляется отдельно | Строки на языке контента прямо в записи |
| **Пользовательское** | Свои шаблоны NPC, правки книжных (копия поверх оригинала, см. 2.10), энкаунтеры, заметки | SQLite, экспорт файлом | Как ввёл мастер |

Правило для спорных случаев: если сомнение между «ядро» и «сервер», выбираем **сервер**, но ядро знает **контракт** записи (какие поля нужны механике). Так DLC добавляется без выпуска новой версии приложения.

### Пакеты контента (DLC)

Каждая запись сервера принадлежит **пакету** (`pack`): `core` (основная книга) или `dlc:<код>`. Мастер выбирает в настройках, какие пакеты включены; фильтры справочников и селекты в листе показывают только включённые. Поле `source` у записи хранит пакет и страницу (`source.book`, `source.page`). Что считается «пакетом», решаем вместе с сервером (7.1); в схемах из 0.7 поле `pack` закладываем сразу.

## 3. Единая форма записи справочника

Каждая запись сервера и ядра, независимо от раздела:

```
uuid, code            -- стабильные идентификаторы (code читаемый: "kevlar", "aikido")
pack                  -- "core" | "dlc:<код>"
name                  -- на языке контента
summary               -- одна фраза: что это (для подсказки при наведении)
details               -- полное описание своими словами (без цитат книги)
source { book, page } -- откуда (печатная страница)
tags                  -- для фильтров
...поля раздела       -- числа, слоты, ссылки на другие записи по code
```

Правила:

- **Описания пишем своими словами**, коротко, с числами и СЛ, как в 2.9b. Цитаты и длинные куски не переносим (раздел 7 роадмапа).
- Ссылки между записями — по `code` (навык ↔ стиль ↔ оружие), а не по названию.
- Подсказка при наведении берёт `summary`; полная карточка в справочнике — `details`. Одна запись — один источник правды для листа и справочника.
- Ядро держит **контракт** (какие поля механике нужны), записи с сервера проходят валидатор контракта при загрузке.

## 4. Боевые искусства и выбор специализации (пример для сервера)

Задача пользователя: селект стилей вместо свободного текста, прокачка стиля, справка по приёмам при наведении, стили из DLC.

Предлагаемая модель (уточняется после вычитки стр. 178–180):

- Запись `martial_art`: `code`, `name`, `pack`, `summary`, `techniques[]` (`code`, `name`, `summary`, `details`, условие открытия, если оно есть), `source`.
- В листе навык «Боевые искусства» остаётся навыком со специализациями (механика строк уже есть, как у языков), но поле «специализация» — **селект по включённым пакетам**; рядом уровень владения этим стилем.
- Приёмы: список в карточке стиля; в листе при наведении на стиль или приём — `summary`.
- Если запись стиля исчезла (пакет выключен, контент обновился), строка в листе **не пропадает**: остаётся с кодом и пометкой «нет в базе».

Так же устроены другие списки специализаций (языки, местность, образование): список — серверная коллекция, лист хранит `code`.

**Что нужно сверить по книге:** сколько стилей в основной книге, как приёмы привязаны к уровню, есть ли у стиля свой тип урона и условия, как книга определяет «прокачку» (очки развития, ИП).

## 6. Цикл вычитки одного раздела

Совпадает с правилами из CLAUDE.md, раздел «Данные из книги»:

1. **Страницы:** текст сплошной — по OCR (`.cache/ocr/p<N>.txt`); таблицы и числа — только по картинкам (`python tools/render-pages.py <от> <до>`, 120 dpi для плотных таблиц).
2. **Двойное извлечение таблиц:** два независимых прохода (второй — отдельным агентом без доступа к первому), сравнение, расхождения перечитать при 150–170 dpi.
3. **Нормализация:** `code`, `source.page`, `pack`, `summary`, `details` своими словами, ключи в обоих языках.
4. **Схема и валидатор:** схема в `schemas/`, инварианты (числа в диапазонах, уникальность `code`, ссылки существуют, у каждой записи есть `source.page`).
5. **Тесты:** golden-тесты по примерам из книги (скилл `rules-golden-test`) там, где есть механика.
6. **Справочник:** раздел, карточка, поиск, подсказка. Новые компоненты по чек-листу `add-ui-component`.
7. **Остаточные сомнения** — вопрос пользователю через `AskUserQuestion` с конкретным местом (страница, строка, два варианта), а не «проверь файл».
8. **Фиксация:** строка в роадмапе (что сделано, что нет); синонимы терминов — в `GLOSSARY.md`.

Признак «раздел готов»: данные проходят валидатор, подсказка и карточка работают на двух языках, тесты зелёные, `npm run check` и `cargo test --workspace` проходят, пользователь посмотрел результат в приложении.

## 7. Риски

- **Лицензия RTG:** публикация таблиц и текстов на сервере зависит от условий Homebrew-лицензии. Локальная вычитка для личного использования от этого не зависит; публикация — зависит. Не хранить и не коммитить OCR всей книги (`.cache/` в `.gitignore`).
- **Нестабильная терминология русской редакции:** один ID на понятие, синонимы в `GLOSSARY.md`; при расхождении текста и таблицы — вопрос пользователю.
- **OCR таблиц:** числа и нотация кубиков искажаются (`1d6` → `196`); числа только с картинок.
- **DLC:** их тексты нужны для вычитки стилей и контента пакетов. Если файлов дополнений нет, сначала проектируем формат, наполняем основной книгой.
- **Объём:** подсказки для всех навыков, приёмы всех стилей и каталог снаряжения — тысячи строк текста на два языка. Чтобы не стопорить, идём разделами; готовый раздел можно показывать, не дожидаясь остальных.

| Боевые искусства (PDF 180–181) | текст приёмов цельный и читаемый: у приёма есть название, **условие** («ВОЛЯ 8 или больше», «вы дважды ударили цель»), СЛ, эффект; стили: Айкидо, Карате, Дзюдо, Тхэквондо + «Общие спецприёмы» |
| **Таблицы** | **не годятся**: колонки разнесены по отдельным блокам, строки не выровнены, значения теряются (таблица передвижения потеряла числа, таблица критических травм головы разложена по столбцам), «СЛ» читается как цифры |

**Как использовать**

1. **Проза** (описания навыков, глоссарий, правила, приёмы стилей): берём из `.cache/book-ocr`, сверяем с картинкой только флаговые страницы и места, где есть числа или СЛ; пишем своими словами.
2. **Таблицы и числа** (СЛ по дистанциям, цены, статы, пороги): только с картинок (двойной проход, как в CLAUDE.md). OCR подсказывает, на какой странице искать.
3. **Пометки «проверить»** (178 страниц) подряд не проходим: проверяем по картинке те, что попали в разделы, которые вычитываем сейчас.

Необязательное пожелание к утилите: отдельный флаг страницы «содержит таблицу» (`has_table`), чтобы такие страницы сразу шли в проход по картинкам.

## 10. Пакеты и синхронизация с сервером

### Как размечать происхождение записи

Предложение: у каждой записи поле **`pack`** (код пакета), рядом с уже существующим `source.page` (страница книги). Они отвечают на разные вопросы:

- `pack` — **в каком издании** запись лежит и **с каким набором** она включается или выключается: `core`, `<код дополнения>`;
- `source.page` — на какой странице этого издания это написано.

Название `source` уже занято страницей, `from` — служебное слово SQL (колонку пришлось бы экранировать), а `pack` читается как есть («пакет»), и по нему же фильтруется справочник. Если вам нравится другое слово (`edition`, `book`), заменим одной правкой схем, пока их ещё нет на сервере.

Описание самого пакета (запись `packs`): `code`, `name` (на языке контента), `kind` (`core` или `dlc`), `summary`, `version`, и **число сущностей по типам**: `{ weapon: 3, armor: 4, npc: 5, martial_art: 6 }`. Админка заполняет его при публикации, приложение показывает в списке пакетов до скачивания («добавляет 3 оружия, 4 брони, 5 NPC, 6 стилей»).

Состояний пакета у мастера два, и они независимы: **скачан** (записи лежат на диске) и **включён** (его записи видны в справочниках, селектах и при выборе шаблонов). Выключенный пакет не удаляет данные и не ломает персонажей: лист хранит `code` записи, а если записи нет или пакет выключен, показывает код с пометкой «нет в базе».

### Сверка хэшем

Идея пользователя: при запуске сравнить хэш локальных данных с хэшем сервера; совпал, значит, ничего качать не надо. Это дешёвая проверка, и она хорошо ложится на «манифест версий» из 0.6/7.4. Предлагаемое устройство:

1. **Хэш записи не считаем.** Считаем хэш **коллекции внутри пакета и языка**: SHA-256 от канонического JSON (ключи отсортированы, пробелы убраны), чтобы одинаковые данные давали одинаковый хэш независимо от порядка полей. Язык входит в ключ, потому что тексты записей на `ru.` и `en.` различаются.
2. **Манифест — одно небольшое сообщение:**
   ```
   root: <хэш всего>
   packs:
     core:      { hash, collections: { weapons: <hash>, armor: <hash>, npc: <hash>, ... } }
     <dlc-код>: { hash, collections: { ... } }
   ```
   `root` — хэш от хэшей пакетов; хэш пакета — от хэшей его коллекций (дерево Меркла, только два уровня).
3. **При запуске:** запрос манифеста (≈ несколько КБ). `root` совпал с локальным: ничего больше не делаем. Не совпал: сравниваем пакеты, затем коллекции, и качаем **только коллекции с другим хэшем**, у которых пакет скачан. Новый пакет сначала просто появляется в списке («доступен»).
4. **Онлайн-режим:** запрос коллекции (`GET /packs/<pack>/<collection>?lang=ru`) отдаёт `ETag` = хэш; повторный запрос с `If-None-Match` возвращает 304. Кэш в SQLite хранит хэш каждой коллекции, поэтому и онлайн-режим, и полная выгрузка используют один и тот же механизм.
5. **Нет сети:** работаем со снимком, кнопка «обновить» недоступна, ошибка не показывается пользователю при запуске, только в статус-зоне при ручном обновлении.

Что хэш **не** даёт: он говорит «изменилось», но не «что». Если мастеру нужно показать, что именно поменялось в шаблоне, который он правил (копия поверх оригинала, 2.10), это отдельная задача (сравнение по `code` и полям при обновлении). Хэш также не защищает от подмены (для этого нужна подпись манифеста); это вопрос безопасности сервера, решать в 7.2.

### Что записи сервера обязаны иметь

`uuid` (глобальный), `code` (читаемый, стабильный в пределах пакета), `pack`, `name`, `summary`, `source { page }`, поля контракта раздела. `code` уникален в рамках типа и **не переиспользуется** после удаления записи (иначе старые листы укажут на чужую запись).

### Что меняется в роадмапе

Задача 7.4 (сверка версий) расширяется схемой выше; в 0.7 (схемы) поле `pack` и тип `packs` закладываются сразу; 2.0b (мастер установки) предлагает выбор пакетов с числом сущностей по типам.

## 11. Быстрая справка по атаке (таблицы СЛ)

Пожелание пользователя: таблицы попадания из книги должны быть под рукой, с выбором «что хочет сделать игрок» по иконке, в нашем стиле. Пользователь предположил, что место — окно урона.

**Замечание.** Окно «Урон получен» открывается, когда попадание уже решено: мастер вводит урон. Таблица СЛ нужна **до** броска атаки (какая сложность на этой дистанции у этого оружия). Поэтому окно урона для неё неудобно, но само окно может ссылаться на ту же справку. Приложение по-прежнему **ничего не считает** (решение 0): таблица только показывает значения.

**Предложение:**

- Кнопка «Справка по атаке» в боевой панели правой колонки (рядом со стартом боя) и горячая клавиша; открывается компактным поповером, не закрывая карточки.
- Верхний ряд — иконки **класса оружия или действия** (пистолет, пистолет-пулемёт, дробовик, штурмовая винтовка, снайперская винтовка, лук, гранатомёт, ракетница, ближний бой, автоогонь, подавление, прицельный выстрел). Клик показывает таблицу СЛ по полосам дистанции, режим и примечания книги. Классы берём из каталога оружия (`WeaponKind`), чтобы иконка и запись оружия связывались по коду.
- Таблицы — **ядро** (часть основной книги правил, не расширяются дополнениями); дополнение с новым классом оружия добавляет свою строку через пакет.
- Когда в окне урона появится выбор оружия, оттуда можно открывать эту справку сразу на нужном классе.

**Решение пользователя:** иконки по **классу оружия** (строка таблицы книги = класс, колонки = полосы дистанции). Автоогонь, подавление и прицельный выстрел идут отдельными кнопками рядом, как режимы.

**Мелочи в той же справке** (отдельные кнопки без класса оружия, у каждой своя карточка «как это работает в книге»):

- **Бросок предмета** (обычный бросок и граната): дальность, СЛ, что происходит при промахе (отклонение), урон гранаты; граната и обычный предмет — две карточки, потому что правила разные;
- другие короткие действия боя, которые мастер вспоминает посреди хода (встать, схватить, подножка, вырваться из захвата, поджечь/потушить, утонуть). Список составляем при вычитке стр. ≈167–180 (этап 4), по одной карточке-сводке;
- каждая карточка — запись `Article` (раздел 3): `summary` (одна фраза), `details` (правило своими словами с числами), `source.page`, ссылка на связанные записи по `code`.

Таблицы и карточки нужно сначала снять с картинок (стр. ≈169–180, двойной проход).

## 12. Английский оригинал на любой справке (отложено)

**Статус: не делаем.** Английского издания у пользователя нет, поэтому русский и английский тексты записей пишем своими словами. Раздел оставлен как проект на случай, если издание появится: в данных от этого ничего не требуется, кроме того, что уже есть (`code`, `source.page`).

Исходное пожелание (для истории):

Пожелание пользователя: на любой справке кнопка «Оригинал» показывает, как это сформулировано в английском издании; переключение можно оформить глитчем (как в остальном интерфейсе).

**Юридический нюанс, который надо решить до реализации.** Наши `summary` и `details` написаны **своими словами** именно ради лицензии R. Talsorian (раздел 7). Оригинальная английская формулировка — это уже **текст книги**. Если кнопка «Оригинал» показывает его из данных, которые мы кладём в приложение или на сервер, мы распространяем текст книги, и это ровно то, чего правила проекта избегают. Поэтому два варианта:

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **A. Локально у мастера (Рекомендация)** | Оригинал не входит ни в приложение, ни в сервер. Мастер сам подключает файл с английским текстом своей книги (его выгрузка OCR/текста), приложение читает его локально и находит абзац по `source.page` и `code` | Ничего чужого не распространяем; работает без решения по лицензии; у каждого мастера свой законно купленный текст | Мастеру надо один раз подключить файл; без него кнопка неактивна («подключите английский текст книги») |
| **B. Входит в данные** | Английский текст лежит в записях или отдельной коллекции `originals` на сервере | Работает из коробки | Требует явного разрешения по лицензии RTG; без него — нельзя |

Рекомендация: **A как основной путь**; B рассматривать, только если проверка лицензии (этап 0) явно это разрешит. Формат одинаков в обоих случаях, поэтому выбор можно отложить: интерфейс и связь записей с оригиналом строятся сразу.

**Устройство (годится для обоих вариантов):**

- Хранилище оригиналов — отдельное от записей, ключ: `code` записи (или `source.page` + номер блока на странице), `lang` (`en`; потом, возможно, другие издания). Запись справочника про оригинал ничего не знает.
- Кнопка «Оригинал» есть на карточке справки и в подсказке при наведении; она неактивна и объясняет почему, если для записи нет оригинала.
- Показ: поповер или режим карточки с английским текстом и страницей книги; переключение «наш текст ↔ оригинал» с коротким глитчем (утилита `glitch-hit` из `index.css`, уже учитывает `prefers-reduced-motion`).
- Источник английского текста: **английское издание книги**, а не русская книга. У нас на руках русский PDF; английский текст пользователь вычитает отдельным проходом (его утилита OCR подходит). Сопоставление абзацев русского и английского изданий идёт по структуре книги (разделы совпадают, нумерация страниц нет) и делается при вычитке записи, а не автоматически.
- Для записей, вычитанных без английского текста, кнопка остаётся неактивной; это не ошибка.

**Что учесть в данных уже сейчас** (чтобы потом не переделывать): у каждой записи есть `code` и `source.page` (раздел 3); у статей правил есть устойчивые идентификаторы блоков (например, `combat.throw.grenade`); английский термин оригинала для названия записи хранится в самой записи (`name` на `en`), он короткий и сам по себе не цитата.

## 13. Требования к серверной части (в план фазы 7)

Решения пользователя о том, как сервер хранит тексты:

1. **Двуязычный ввод в админке.** У каждого текстового поля записи (название, `summary`, `details`, заметки) в админке два ввода: «Текст ру» и «Текст en». Запись нельзя опубликовать, если заполнен только один язык (пустой английский допускается только явной пометкой «пока без перевода», тогда приложение показывает русский как запасной).
2. **Локали живут в той же базе.** Строки интерфейса и ядра (то, что сейчас лежит в `ru.json`/`en.json`) тоже хранятся на сервере, ключ → текст на двух языках, и редактируются в той же админке. Это канал, по которому тексты можно поправить без выпуска новой версии приложения.
3. **Слои не меняются.** Ядро и интерфейс обязаны работать офлайн с первой минуты, поэтому в приложение по-прежнему вшит снимок локалей (`ru.json`/`en.json`). Серверные локали **накладываются поверх** вшитых (ключ с сервера побеждает) и приходят тем же механизмом хэшей (раздел 10): отдельная коллекция `locales` в манифесте, хэш на язык.
4. **Одна проверка парности.** Тот же инвариант, что сегодня у `tools/check-i18n.mjs` (ключ есть в обоих языках, плейсхолдеры `{{…}}` совпадают), выполняет сервер при публикации и не даёт сохранить расхождение.

**Что это значит для задач фазы 7:**

- 7.1 (контракт API): коллекции `packs`, `locales` и типы записей несут оба языка; ответ может быть запрошен на одном языке (`?lang=`) или целиком для выгрузки;
- 7.2 (сервер и база): текстовые поля хранятся парами `ru`/`en` (или отдельной таблицей переводов), а не в разных базах на каждый язык;
- 7.7 (админка): редактор с двумя вводами на поле, редактор ключей локалей, проверка парности, публикация пакета со счётчиками по типам (раздел 10);
- 2.0 (уже в роадмапе): решение «две базы по адресам `ru.`/`en.`» превращается в «одна база, язык выбирается параметром»; адреса можно сохранить как алиасы.

**Вопрос к пользователю.** Я понял «локали тоже пишем в той базе» как «серверные локали накладываются на вшитые». Если имелось в виду, что вшитых локалей вообще не будет (всё с сервера), это ломает первый запуск без сети; тогда нужен хотя бы минимальный вшитый набор (названия вкладок, ошибки загрузки).

## 14. Языки приложения: один установщик, язык выбирается при установке

Решение пользователя: приложение выходит на русском и на английском; на сайте **один установщик**, а какой язык поставить, мастер установки спрашивает при установке. Для английского сообщества это не уникальный продукт (существует более старый компаньон Sheridan), но версия остаётся в плане: язык уже сделан, цена небольшая.

**Устройство (решение пользователя):**

- **Один установщик, один набор файлов.** В нём лежат локали интерфейса обоих языков (они небольшие) и снимки контента обоих языков. В мастере установки пользователь выбирает, какой язык поставить: **ru**, **en** или **ru + en**. Выбор сохраняется в настройках: язык интерфейса по умолчанию и набор языков, контент которых доступен. Выбор не является навсегда: язык можно добавить или убрать позже в настройках.
- **Где живёт сам выбор:** страница выбора языка в установщике или первый запуск приложения. Рекомендация: **мастер первого запуска внутри приложения** (он нужен и для выбора пакетов, 2.0b), а установщик только подставляет язык системы как значение по умолчанию. Это можно уточнить при реализации: данные и логика от места вопроса не зависят.
- **Дополнительные языки и пакеты** докачиваются с сервера (механизм хэшей, раздел 10; хэш считается на язык), поэтому «добавить английский» позже работает так же, как «добавить пакет».
- **Переключение языка в приложении:** если контент нужного языка есть, переключение мгновенное; если нет, приложение предлагает докачать его и до тех пор показывает контент текущего языка. Интерфейс переключается всегда (локали вшиты).
- **Пользовательские данные не зависят от сборки.** Персонажи, сессии и экспорт хранят ID записей, поэтому файл, сделанный в ru-сборке, открывается в en-сборке. Исключения: имена и заметки, которые ввёл сам мастер, остаются на языке ввода.

**Что надо учесть в работе:**

1. **Сборка:** один артефакт; в нём оба снимка контента и обе локали; настройка выбранных языков хранится в SQLite/конфиге и меняется без переустановки.
2. **Сайт:** одна кнопка скачивания, описание на двух языках.
3. **Копии книжных шаблонов** (2.10): копия хранит текст того языка, на котором её правили, и не переводится при смене языка. Это стоит показать мастеру (метка языка на копии) или учесть при слиянии с обновлением оригинала.
4. **Качество английского текста.** У нас нет английского издания, поэтому английские названия и термины (приёмы, предметы, состояния) мы подбираем сами, а не берём из официальной локализации. Часть терминов может не совпасть с официальными: игроки, знающие английскую книгу, это заметят. Меры: держать список терминов в `GLOSSARY.md` с колонкой «официальный английский термин (проверить)»; в английской версии указать, что тексты неофициальные; позже дать сообществу способ исправлять формулировки (правки через админку, раздел 13).
5. **Админка и локали на сервере** (раздел 13) нужны как раз для этого: английские тексты можно улучшать без выпуска новой версии.

**Задачи в роадмапе:** 2.12 (выбор языков, настройки языков), расширение 2.0b.

### Лицензия RTG (Homebrew Content Policy, 22.03.2021)

Прочитан первоисточник (rtalsoriangames.com/homebrew-content-policy), я не юрист. Что важно для проекта:

- Контент должен быть **бесплатным**; платить за него и продавать на торговых площадках нельзя. Пожертвования и реклама допустимы, если они не закрывают доступ.
- Нельзя использовать названия игр и книг RTG в своём названии, а также их цвета, фирменные шрифты и оформление (исключение — копировать вид статблоков, скримлистов, листов персонажей). Арт из книг без письменного разрешения нельзя.
- «Нельзя воспроизводить текст из игр, книг и продуктов», включая статблоки и свод правил. Можно ссылаться на именованных персонажей и места.
- **Приложения и VTT:** листы персонажей и генераторы разрешены, в том числе автоматизация бросков и случайного контента (жизненный путь, ночные рынки). Но «контент не может включать больше, чем краткое изложение материала», и **нельзя давать полные статблоки NPC, угроз и защит в любом виде**.
- **Игровые помощники** могут излагать кратко и воспроизводить таблицы и схемы «когда нужно», но не должны излагать правила так полно, чтобы книга стала не нужна, и не должны дублировать функцию продукта RTG.
- Если контент опубликован не в виде поста на форуме, нужна заметная пометка: «неофициальный контент по Homebrew Content Policy R. Talsorian Games, не одобрен и не поддерживается RTG». RTG может потребовать снять контент с любой площадки.
- Про переводы политика ничего не говорит.

**Что это значит для решений 9.3 (таблицы переносим) и NPC:**

1. Всё, что мы пишем своими словами как краткое изложение (описания навыков, сводки правил, приёмы) — в рамках политики.
2. **Книжные NPC (шаблоны, стр. 412–416) — полные статблоки**: для публичной раздачи (сервер, установщик с данными) это прямо запрещено. Для личного использования не мешает.
3. **Таблицы** (СЛ по дистанциям, цены, оружие, броня) допустимы только как «игровой помощник» и в том объёме, чтобы книга оставалась нужной; серверные каталоги оружия и брони с полными числами — серая зона.
4. Нужна пометка о неофициальном контенте в приложении и на сайте; название «Red Companion» и красно-чёрное оформление не должны имитировать фирменный стиль RTG.
5. Бесплатность: приложение с этим контентом нельзя продавать.

**Решение пользователя (опросом):** книжные шаблоны NPC и таблицы пока остаются как есть, вопрос решается **перед публикацией** (раздачей приложения или запуском сервера, фаза 7). Вычитка идёт в формате «краткое изложение своими словами». Перед публикацией: убрать или заменить книжные NPC, оценить серверные таблицы, добавить пометку о неофициальном контенте. **Статус прав:** пользователь написал в RTG и ведёт вопрос сам. Запасной план, если откажут: шаблоны NPC раздаются отдельно как пользовательский контент (файлы импорта шаблонов, 2.4b), а в поставку приложения не входят.
