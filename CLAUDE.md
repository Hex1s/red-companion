# Red Companion

Десктопный GM-companion для настольной ролевой игры **Cyberpunk RED**. Tauri (Rust-бэкенд) + React-фронт. План работ — `docs/ROADMAP.md` (читай его перед любой крупной задачей). Исходник правил — `docs/cyberpunkRedBook.pdf` (русская редакция; текстовый слой нечитаем, страницы читаются только как картинки).

## Язык

- Код, идентификаторы, комментарии в коде, сообщения коммитов — **английский**.
- Документация (`docs/`, этот файл, README) — **русский**.
- Ответы пользователю — русский.

## Работа по плану

- Перед задачей прочитай `docs/ROADMAP.md`: статусы `[ ]` / `[~]` / `[x]` стоят у каждой задачи. Бери следующую невыполненную задачу **текущей фазы**, уважая колонку «Зависит от».
- Когда начинаешь задачу — поставь `[~]`, когда закончил и проверил (типы, тесты; визуально проверяет пользователь, см. «Запуск приложения») — `[x]`. Если задача выполнена частично, оставь `[~]` и допиши в ячейке, что сделано.
- Новые задачи, которые всплыли по ходу работы, добавляй в роадмап с номером и зависимостью, а не держи в голове.

## Git

- **Сам ничего не коммить** и не пушь: ни `git commit`, ни `git push`, ни `git add` под коммит. Коммиты делает пользователь. По завершении задачи оставляй изменения в рабочем дереве и предлагай текст сообщения коммита (английский), если он нужен.

## Запуск приложения

- **Никогда не запускай приложение сам** (`npm run tauri dev`, `npm run dev`, `cargo run`, headless-браузер и т. п.) и **не смотри на него**: ни скриншотов окна, ни захвата экрана, ни подключения к WebView, ни управления окном. Приложение запускает и смотрит **только пользователь**.
- Проверяй своими средствами: `cargo test --workspace`, `npm run check`, `npx tsc --noEmit`. Про визуальные правки пиши, что именно изменилось и куда смотреть, и проси пользователя проверить.

## Инструменты и скиллы

- `tools/render-pages.py` — рендер страниц книги в PNG (`python tools/render-pages.py 168 175`). Печатная страница N = страница PDF N+1.
- `tools/import-ocr.py` — раскладывает готовый OCR всей книги (утилита `pdf-reader`) по печатным страницам в `.cache/book-ocr/`; пометки «проверить» лежат в `index.json`.
- `tools/ocr-pages.py` — OCR страниц через Tesseract (русский + английский) в `.cache/ocr/`. Годится для сплошного текста; **таблицы и числа из OCR не брать**, сверять по картинке страницы.
- Проектные скиллы в `.claude/skills/`: `read-rulebook` (как читать книгу и где какая глава), `add-ui-component` (чек-лист дизайн-системы), `rules-golden-test` (тесты правил по примерам из книги). Вызывай их, когда задача подходит.

## Данные из книги (без ручной вычитки пользователем)

Пользователь **не вычитывает** данные. Поэтому:

- Числа берутся только с картинки страницы (не из OCR) и вносятся в seed-данные со ссылкой на источник: поле `source.page` (печатная страница).
- Каждая таблица извлекается **дважды независимо** (второй проход — отдельным агентом без доступа к первому результату), результаты сравниваются; расхождения перечитываются с увеличенным dpi.
- Проверки в коде: контрольные суммы и инварианты (в таблице критических травм 11 строк на 2d6 от 2 до 12; ОС и ПЗ — целые числа в разумных диапазонах; у всех записей есть `source.page` и ключи локализации в обоих языках), плюс golden-тесты по примерам из книги.
- Если после этого остаётся сомнение, спрашивай пользователя через `AskUserQuestion`, показывая конкретное место (страница, строка, два варианта), а не просьбой «проверь файл».
- Полный OCR книги сделан отдельной утилитой пользователя (`D:\projects\pdf-reader`, результат — `output/cyberpunkRedBook.json`); `python tools/import-ocr.py <путь к json>` раскладывает его в `.cache/book-ocr/p<N>.txt` по печатным страницам. Проза годится для черновиков, таблицы и числа — только с картинок. Что вычитывать и куда класть — `docs/BOOK-PLAN.md`.

## Неясные ситуации

При любой неясности — спорное правило книги, выбор между вариантами реализации, расхождение между ROADMAP и кодом, конфликт зависимостей, неочевидное решение по дизайну — **не угадывай и не выбирай молча**. Задай вопрос пользователю **опросом в консоли** (`AskUserQuestion`): 2–4 варианта с описанием, рекомендуемый — первым, с пометкой «(Recommended)». Свободный ввод пользователь всегда может дать через «Other». После ответа зафиксируй решение там, где оно будет жить (ROADMAP, этот файл или код).

## Архитектура

- **Rust (`src-tauri/`, позже крейт `rules-core`)** — источник правды: правила, расчёт урона, кубики, хранилище (SQLite), доступ к справочникам через трейт `DataSource`. Без зависимостей от Tauri в `rules-core`.
- **React (`src/`)** — только отображение. Данные и расчёты получает командами Tauri; в Zustand хранится **только UI-состояние** (выбранная вкладка, выбранный персонаж).
- **Справочники** (оружие, броня, NPC и т. д.) приходят через один слой `DataSource`. UI не знает, откуда данные: встроенный снимок, кэш или API (сервер — последняя фаза).
- Бой абстрагирован до события «Урон получен» (см. ROADMAP, раздел 0). Расчёты попадания, дальности и СЛ **не реализуем**.

## Команды

- `npm run dev` — только фронт (Vite, порт 1420).
- `npm run tauri dev` — приложение целиком.
- `npx tsc --noEmit` — проверка типов (обязательно перед завершением работы над фронтом).
- `npm run build` — типы + production-сборка фронта.
- Хук `.claude/settings.json` сам запускает `npm run check` после правок в `src/**/*.ts(x)` и в `ru.json`/`en.json` (`tools/post-edit-check.mjs`); если он вернул ошибку, исправь её до завершения.
- `python tools/gen-glossary.py` пересобирает `docs/GLOSSARY.md` (локали + seed); руками в глоссарии правятся только синонимы в скрипте.

## Стек фронта

React 19, TypeScript (strict), Vite, Tailwind v4 (`@tailwindcss/vite`, конфиг в CSS — файла `tailwind.config` нет), shadcn/ui (стиль new-york, компоненты в `src/components/ui/`), Zustand, react-hook-form + zod, i18next. Алиас `@` → `src/`.

Шрифты (все с кириллицей, ставятся пакетами `@fontsource-variable/*`, работают офлайн). Консольный вид, пара из двух шрифтов (решение пользователя):
- весь текст, подписи и числа — **JetBrains Mono** (`font-sans` и `font-mono` указывают на него; класс `num` добавляет `tabular-nums`),
- заголовки и кнопки — **Tektur** (`font-display`), заглавные.

Не использовать Orbitron, Rajdhani, Share Tech Mono, Oxanium, Chakra Petch: в них нет кириллицы. Inter убран (был шрифтом текста до QA-правки 1.28).

## Дизайн-система: «тактический HUD»

Только тёмная тема (`<html class="dark">`), светлой нет. Фон почти чёрный, плотные панели с тонкой рамкой 1px, красный акцент (`--primary`, ≈ #d6302b). Цвет несёт смысл: красный — действие и урон, цвета `state-*` — состояние персонажа.

**Правила для каждого нового компонента:**

1. **Все тексты только через i18n.** Никаких захардкоженных русских или английских строк в JSX. Ключ добавляется **в оба** файла: `src/i18n/locales/ru.json` и `en.json`. Хук — `useTranslation()`.
2. **Только токены цвета.** Никаких hex, `rgb()` и палитры Tailwind (`red-500`) в компонентах: `bg-primary`, `text-muted-foreground`, `bg-state-ok` и т. д. Новый цвет сначала заводится токеном в `src/index.css` (`:root` + `@theme inline`). **Единственное исключение — цветовая метка персонажа (2.16):** цвет выбирает мастер из палитры в 16 цветов (`src/lib/mark-palette.ts`, значение хранится как `#rrggbb`; старые произвольные цвета продолжают показываться), это пользовательские данные; он применяется через `style`/CSS-переменную из значения в данных, в компонентах литералов цвета по-прежнему нет.
3. **Числа всегда с классом `num`.** ПЗ, ОС, инициатива, броски, статы — моноширинный шрифт с `tabular-nums`.
4. **Срезанные углы только через `cut`.** Никаких самописных `clip-path` в компонентах. Вариации — через переменные `--cut` (размер среза), `--cut-border`, `--cut-fill` (например `[--cut:6px]`, `[--cut-border:var(--primary)]`). `cut` рисует рамку фоном элемента, а заливку псевдоэлементом, поэтому **не вешай `border` и `bg-*` на элемент с `cut`**; цвета задавай через `--cut-border` / `--cut-fill`.
5. **Радиус 0.** Скруглений нет (`--radius: 0px`); `rounded-*` не использовать.
6. **Заголовки** `h1`–`h4` автоматически Tektur, заглавные, с разрядкой. Кнопки — тоже Tektur, заглавные.
7. Новые shadcn-компоненты добавлять так: `npx shadcn@4.21.0 add <name>` (версия зафиксирована; CLI не может сам доставить зависимости и падает на `EALLOWSCRIPTS` — если компоненту нужен новый пакет, поставь его вручную через `npm i`). После добавления привести к стилю выше (радиус, `cut`, шрифты). Компоненты shadcn импортируют `cn` из пакета `cn`; в самописном коде используй `cn` из `@/lib/utils`.
8. Состояния ранения красятся токенами: `state-ok` (полные ПЗ), `state-light` (< макс), `state-serious` (< ½), `state-mortal` (< 1), `state-dead`.
9. Персонаж за укрытием: контактная полоса платы карточки (`--gold`) и кнопка-щит цветом `cover` (сталь-синий), это не цвет ранения. Внешней рамки у карточки нет: активный ход — красная планка слева и лёгкая красная заливка платы, выбранная карточка — серая планка.
10. **Статус-зона** (правый нижний угол рабочей области, `StatusArea`; в коде `status.show(...)` / `status.error(...)` из `@/store/status-store`): сохранение (спиннер → галочка «Сохранено»), результат действий, ошибки команд. Не `window.alert` и не красная строка в странице. Одинаковый `id` — это то же сообщение: оно обновляется на месте, а не копится. Ошибки остаются, пока их не закроют крестиком; ошибки внутри диалога остаются в самом диалоге (модалка блокирует клики вне себя).
11. **Ошибка в поле** — только через `FieldBadge` (`components/ui/field-badge.tsx`): красный «!» в круге, центр которого — правый верхний угол поля, тултип с причиной. Он не занимает места и появляется после паузы или ухода из поля, чтобы не мигать при наборе; рамка поля краснеет тем же состоянием (`invalid` из render-prop). Красных строк-ошибок под полями нет. Это единственное место, где разрешён `rounded-full`.
12. **Золото бренда** (`--brand`, `bg-brand`): только конструкция (акцент шапки, подчёркивание активной вкладки, контактная полоса карточки), не текст, не числа, не кнопки действий и не состояния: `state-light` — жёлтый со смыслом.
13. **Иконки — Material Symbols, стиль Sharp, weight 400** (`@/components/ui/icons`, не `lucide-react`: пакет удалён). Компоненты называются как в lucide (`X`, `Plus`, `Swords`...), по имени глифа — `<Icon name="favorite" />`. Файл `icons.tsx` **генерируется** `python tools/gen-icons.py <путь к @material-symbols/svg-400/sharp>` (пакет скачать `npm pack @material-symbols/svg-400` в папку вне репозитория); руками файл не править — новый глиф добавляется в скрипт. Размер по умолчанию 24 px, меняется классом `size-*`. Новый shadcn-компонент, принёсший `lucide-react`, переводить на эти иконки (в `components.json` `iconLibrary` остался `lucide` только для CLI).

## Раскладка

Шапка с вкладками (Персонажи / Энкаунтеры / Справочники) и переключателем сессий (у каждой сессии своя сцена, бой и состав; персонажи общие, сессия хранит ссылки) → основная область под текст (лист выбранного персонажа, страница справочника) → справа колонка сессии: небольшие кнопки боя сверху (старт, следующий ход, конец, отмена последнего урона) и карточки персонажей **активной сессии** с инициативой, укрытием, «Уроном», спасброском. Вкладки «Бой» нет: бой целиком ведётся с колонки. Каркас — `src/components/layout/app-shell.tsx`.

## Структура `src/`

- `components/ui/` — shadcn-примитивы.
- `components/layout/` — каркас приложения.
- `components/character/` — всё, что про персонажей (карточка, полоса ПЗ).
- `i18n/` — настройка i18next и `locales/{ru,en}.json`.
- `lib/` — утилиты.

Файлы — kebab-case, компоненты — именованные экспорты PascalCase, пропсы — `type XProps`, без `any`.

## Локализация

- Языки: `ru` (основной), `en`; запасной — `en`.
- Аббревиатуры статов русской редакции: РЕА=REF, ЛВК=DEX, ТЕЛ=BODY, ХАР=COOL, ЭМП=EMP, СКО=MOVE, УДЧ=LUCK, ПЗ=HP, ОС=SP, ЧЕЛ=HUM, СЛ=DV.
- **Две группы текстов.** Ядро правил (травмы, навыки) и интерфейс — ключи i18n в `ru.json`/`en.json`. Серверный контент (укрытия, щиты, броня, NPC, оружие, лор) приходит строками на языке сервера (`name`, `gear`, … в записи, у записи `uuid` и `code`), ключей в локалях у него нет; язык контента следует языку интерфейса (`set_content_lang`).
- Термины правил держать с устойчивыми ID-ключами (в русской книге терминология плавает, например «Сломанная нога» / «Перелом ноги»).

## Ошибки (Rust → UI)

Пользователь не должен видеть английский текст разработчика. Каждая ошибка, которая может дойти до UI, приходит на фронт как `AppError { code, params, message, cause }` и переводится по коду.

- **Новый вариант в enum ошибок** (`thiserror`, в `rules-core`) = новая арма в `crates/rules-core/src/error_codes.rs`: `match` исчерпывающий, без `_`, одна арма на одной строке `Pattern => "domain.name"` (тест читает коды из этого файла). Параметры для `{{плейсхолдеров}}` — в `params()` через `params!`; вложенную причину — в `cause_info()`; `#[error("…")]` остаётся английским текстом для разработчика (уходит в `message`).
- **Новый enum ошибок** — `impl ErrorInfo` в `error_codes.rs` и строка в `from_rules_error!` в `src-tauri/src/error.rs`.
- **Ошибки самой команды** (не найдено, неверный ввод, нечего делать) — не `format!(…)` и не `String`, а именованный конструктор `CmdError::…` в `src-tauri/src/error.rs` с кодом и `params`. Команды возвращают `Result<T, CmdError>`, никогда `Result<T, String>`; `.map_err(|e| e.to_string())` не писать.
- **Перевод обязателен в обоих языках**: ключ `errors.<code>` (точки кода = вложенность JSON) в `ru.json` и `en.json`. Текст говорит, что случилось **и что делать дальше** («Обновите список», «Попробуйте ещё раз», «Сначала стабилизируйте цель»); без внутренних терминов (`lock poisoned`, `schema`). Коды, созданные вне `error_codes.rs` (конструкторы `CmdError`), добавить в список теста `every_error_code_is_translated_in_both_languages` (`src-tauri/src/error.rs`) — иначе тест их не проверит.
- **На фронте** текст ошибки берётся только через `errorMessage(e)` из `@/lib/errors`; свои `e instanceof Error ? e.message : String(e)` не писать. Технические детали (английский `message`) — `errorDetails(e)`, и только как сворачиваемый блок, не основной текст.
- Проверка перед завершением: `cargo test --workspace` (тест перевода кодов) и `npm run check`.

## Формы и данные

- Формы — react-hook-form + zod (`@hookform/resolvers` версии **5.x**; 6.0 тянет конфликтующие peer-зависимости).
- Экспорт/импорт персонажей — версионированный JSON (`schema_version`); zod-схемы переиспользуются для валидации импорта.
- Каждый бросок кубиков должен допускать ручной ввод результата с физических кубиков.

## Чего не делать

- Не считать попадание, дальность, СЛ, автоогонь в приложении (мастер решает сам).
- Не класть правила и данные в React-состояние: они в Rust.
- Не добавлять светлую тему, скругления, градиенты и неоновое свечение.
- Не распространять тексты и таблицы из книги в репозитории без проверки лицензии R. Talsorian Games.
