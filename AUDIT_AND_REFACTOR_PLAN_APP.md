# Аудит и план к релизу 1.0.0 (приложение + сервер)

Дата аудита: 2026-10-27. Состояние: приложение `ba67269` (main), сервер `57e23df` (master). Код не менялся; из проверок запускался только `npm run check` в приложении (проходит: `tsc`, 1241 ключ i18n в обоих языках). `cargo test` и тесты сервера (нужен PostgreSQL) **не запускались**: всё, что про их результат, взято из чтения кода. Там, где вывод держится на знании Tauri/Next, а не на коде репозиториев, стоит пометка «проверить».

Источники: `docs/SERVER-SPEC.md` (обе копии), `docs/ROADMAP.md`, `docs/deploy-checklist.md` сервера, оба `CLAUDE.md`, исходники `src-tauri/`, `crates/`, `src/`, `.github/workflows/`, `tools/upload-release.mjs`; на сервере `src/lib/api/*`, `src/lib/app/*`, `src/lib/content/*`, `prisma/schema.prisma`, `deploy/*`, `Dockerfile`, workflows.

## Краткое резюме

1. **Сервер готов в коде (S0–S10), приложение к нему не подключено.** В приложении нет ни HTTP-клиента, ни `tauri-plugin-updater`, ни регистрации установки, ни проверки подписи манифеста (`Cargo.toml` без `reqwest`/updater; задачи 7.3, 7.4, 7.5, 7.8 в ROADMAP — `[ ]`; ключей `server.*` в `ru.json`/`en.json` нет). Сервер ни разу не разворачивался на VPS, релизный конвейер (`release.yml` → `tools/upload-release.mjs` → `/api/ci/app-releases`) ни разу не прогонялся на настоящем теге. Стык двух репозиториев сегодня существует только на бумаге и в тестах сервера.
2. **Главный риск 1.0.0 — updater как «дверь в одну сторону».** Что бы ни ушло в 1.0.0, оно становится базой, через которую пройдёт каждое следующее обновление. Если в 1.0.0 не будет рабочего updater с правильным публичным ключом и правильным способом авторизации, все пользователи останутся на 1.0.0 навсегда (или будут ставить новые версии руками).
3. **Рекомендация по объёму 1.0.0:** минимум — регистрация установки + проверка подписанного манифеста + рабочее автообновление + «О приложении»/changelog. Синхронизацию справочников (7.3–7.5) можно выпустить в 1.1 **через тот же updater**: встроенный снимок работает офлайн, а контентное ядро уже отделено трейтом `DataSource`. Это резко сокращает риск, но только если updater проверен на реальной паре версий до тега 1.0.0.
4. **Самая тонкая точка контракта:** хэши коллекций. Сервер подгоняет данные под «типизированный раунд-трип Rust» (`normalize.ts` дописывает `serde(default)`-поля из JSON Schema), потому что приложение хэширует после загрузки в структуры. Любое отличие (лишний `null`, новое поле, которое `serde` молча отбросит) делает загруженную коллекцию непроверяемой. Клиент должен проверять хэш **по полученному JSON**, а не по типизированной структуре (раздел «Несогласованности», C1).
5. **Данные мастера — единственный невоспроизводимый актив:** SQLite без бэкапа перед миграциями, без `busy_timeout`/WAL, без защиты от второго экземпляра, а `Storage::open(...)?` в `setup` при ошибке закрывает приложение без окна и объяснений.
6. **Вне кода:** лицензия R. Talsorian (публикация книжных данных и репозитория), подпись установщиков (Windows SmartScreen, macOS Gatekeeper), политика данных, ключи (updater-ключ ещё не выпущен), развёртывание VPS.

## Критичные проблемы (блокеры релиза)

### B1. Клиентская половина интеграции не реализована

- **Факт.** `src-tauri/Cargo.toml`: зависимости только `tauri` (`tray-icon`), `tauri-plugin-opener`, `serde`, `image`, `webp`, `base64`. `src-tauri/src/lib.rs`: 95 команд, ни одной сетевой. `grep` по `reqwest|updater|installations|red-companion.ru|ed25519|manifest` в `src-tauri/` и `src/` — пусто (совпадения только в `catalog.rs`/`data_source.rs`/`character.rs` про версии коллекций).
- **Что нужно минимум для 1.0.0** (сервер всё это уже отдаёт): `POST /api/v1/installations` → токен (хранить вне логов; таблица в SQLite или хранилище ключей ОС); `GET /api/v1/manifest` с проверкой Ed25519 по вшитому публичному ключу; блок `app` (`latest`, `min_supported`); updater; экран «О приложении» (`GET /api/v1/about`) с вшитым запасным текстом.
- **Что не обязательно для 1.0.0:** `ApiDataSource`, кэш коллекций, режимы «онлайн/локально» (7.3–7.5).
- Решение по объёму — вопрос Q1; зависимости и порядок — в плане (P0-1…P0-4).

### B2. Updater не настроен, а `createUpdaterArtifacts: true` ломает первую сборку

- `src-tauri/tauri.conf.json`: `bundle.createUpdaterArtifacts: true`, но **нет** `plugins.updater` (`pubkey`, `endpoints`), нет зависимости `tauri-plugin-updater`, нет `.plugin(...)` в `run()` (lib.rs:1975), нет разрешения `updater:default` в `capabilities/default.json` (сейчас только `core:default`, `opener:default`), нет способа перезапуска (`tauri-plugin-process` или `app.restart()`).
- ROADMAP 8.5 это уже признаёт: без `pubkey` `tauri build` падает; локальная сборка требует `TAURI_SIGNING_PRIVATE_KEY`. Значит **сегодня ни тег `v1.0.0`, ни обычный `tauri build` на машине владельца не дадут артефактов**.
- Ключ updater (`npx tauri signer generate`) ещё не выпущен (deploy-checklist §2); его потеря = ручная переустановка на Windows/macOS. Ключ подписи манифеста сервера уже выпущен (публичная часть в checklist §5).
- **Нужно до тега:** выпустить ключ, прописать `pubkey` и `endpoints`, подключить плагин и разрешения, положить секреты в GitHub, затем **реально обновиться с тестовой сборки N до N+1 через сервер** (checklist §6 описывает прогон с фальшивыми артефактами, но проверка подписи там включается только «для настоящей проверки» — этого мало, нужна пара настоящих подписанных установщиков, включая установку обновления на чистой Windows).
- **Ротация ключа.** Конфиг плагина принимает один `pubkey`. Если после 1.0.0 ключ придётся менять, старые установки обновить будет нечем. Дешёвая страховка до 1.0: собирать updater в Rust (`app.updater_builder()`), где можно перебирать несколько ключей, и вшить запасной публичный ключ (проверить по документации плагина, какие именно методы билдера доступны в используемой версии).

### B3. Эндпоинт updater требует токен установки; регистрация ограничена 10 в сутки с IP

- `getAppUpdate` (сервер, `src/lib/api/app.ts`) начинается с `authenticate(db, request)`. Токен получается только через `POST /installations`, где `rateLimit(..., installationsPerDay()=10, 86400)` и ещё nginx `limit_req zone=rc_install rate=10r/m`.
- Сценарий: пользователи за общим NAT/CGNAT (общежитие, клуб, мобильные операторы), первый запуск без сети, 429 при регистрации → у установки нет токена → **она никогда не получит обновление и не узнает о `min_supported`**. Пакеты и так публичны (`/releases/{version}/{file}` без авторизации, подписаны minisign), так что токен на `/app/update` ничего не защищает.
- Статический конфиг Tauri не умеет класть персональный токен в заголовок; передать его можно программно (`updater_builder().header(...)` / `check({ headers })` — проверить по документации плагина).
- **Решение (сервер):** отдать `GET /api/v1/app/update/...` анонимно с лимитом по хэшу IP (отдельный счётчик, например 60/час), либо принимать токен «если есть». Клиент в любом случае шлёт `X-App-Version`. Зависит от решения Q2.

### B4. Релизный конвейер и сервер не проверены вживую

- `release.yml` и `upload-release.mjs` написаны «вслепую» (ROADMAP 8.5, checklist §9). Не проверено: имена артефактов Tauri для NSIS/`.app.tar.gz` (`find` в шаге «Collect files» ждёт `*-setup.exe`, `*.app.tar.gz` и `.sig`), совпадение имён с `slots` в скрипте (ровно один файл на слот или ошибка), потоковая загрузка >100 МБ через nginx (`client_max_body_size 1100m` только на `/api/ci/`), публикация, появление блока `app` в манифесте.
- Сервер: `deploy/*`, `deploy.sh`, `deploy.yml` «на настоящем VPS и сквозной выкладке не проверялись» (checklist §8.10). Не выполнены пункты checklist §4 (DNS, TLS, миграции, импорт, владелец админки, токен CI, бэкапы, мониторинг) — все `[ ]`. Проверка восстановления из бэкапа — раз до запуска.
- **Условие выпуска:** один полный репетиционный релиз (`0.9.0`→`0.9.1` или аналог) с настоящими подписями на настоящем VPS, потом `v1.0.0`.

### B5. Подпись манифеста: нет общего тестового вектора, формула `root` не задокументирована

- `contracts/schemas/hash-vectors.json` покрывает только хэши коллекций. Для подписи манифеста (Ed25519 по каноническому JSON без поля `signature`, `signing.ts`) нет ни примера «манифест + подпись + публичный ключ», ни теста на стороне Rust. Приложение будет первым и единственным независимым реализатором — при расхождении (числа, экранирование, порядок ключей) подпись не сойдётся и это обнаружится уже на пользователях.
- Каноникализация на сервере (`canonical.ts`): ключи по байтам UTF-8, `JSON.stringify` для строк и чисел. В Rust `serde_json::Value` без `preserve_order` тоже сортирует по байтам; для целых и обычных строк результат совпадает. **Отличие возможно у нецелых чисел** (`1.0` в Rust-данных против `1` в JS). В текущих seed нецелых чисел нет (проверено `grep` по `crates/rules-core/data/seed`), но защиты нет: цена `0.5` из админки сломает хэш коллекции у приложения. Нужен инвариант «только целые» в zod-схемах сервера или явное правило канонизации.
- Спецификация (§5) говорит «`root` = хэш от хэшей пакетов»; в коде (`release.ts`, `buildContent`) `root = sha256(canonicalize({ packs, pack_meta, locales }))`, где `pack_meta` — хэши названий/описаний пакетов. Если приложение когда-нибудь будет пересчитывать `root` само, оно посчитает иначе. Нужно описать формулу в контракте и добавить вектор.
- **Решение:** сервер генерирует `contracts/manifest-vectors.json` (тестовая пара ключей, манифест с блоком `app` и без, подпись); в приложении тест `verify_manifest` на этих векторах. Сначала правится сервер, потом `contracts:sync`.

### B6. Юридическое и публичное: нужны решения владельца

- Приложение и сервер раздают данные по книге (оружие, броня, роли, шаблоны NPC) в виде пересказа. CLAUDE.md приложения прямо запрещает распространять тексты/таблицы без проверки лицензии R. Talsorian Games; BOOK-PLAN (раздел 0) называет это блокером публикации на сервер; SERVER-SPEC (решение 4) перекладывает ответственность на владельца. Токен можно получить анонимно, значит данные доступны любому.
- Нет `LICENSE` приложения, `README.md` — шаблон Tauri (`# Tauri + React + Typescript`), нет страницы «неофициальный материал» в самом приложении (в спецификации «предложение»). Политика данных на сайте есть (`content/site.ts` → `dataPolicy`), её актуальность надо сверить с реальным набором полей `Installation` (версия, ОС, язык, время визита, хэш IP).
- От этого зависит открытость репозитория (Q6), бесплатная подпись SignPath и лимиты Actions.

## Важные проблемы

### I1. Данные мастера: нет защиты при обновлении схемы и при сбое открытия

- `crates/storage/src/lib.rs:init`: только `PRAGMA foreign_keys`. Нет `journal_mode=WAL`, `synchronous`, явного `busy_timeout` (у `rusqlite` есть таймаут по умолчанию, но поведение при двух процессах не проверялось), нет проверки целостности.
- Нет копии БД перед миграциями refinery (миграции V1–V5 уже были; с 1.0.0 каждая следующая приходит через updater). Откат версии приложения (пользователь поставил старый установщик поверх нового): в БД уже применены миграции, которых нет в старом бинарнике, и refinery по умолчанию на этом прерывает запуск → `Storage::open(...)?` в `setup` (lib.rs:1989) возвращает ошибку → приложение завершается **без окна и без сообщения** (проверить, как ведёт себя ошибка `setup` в релизной сборке на Windows).
- Нет `tauri-plugin-single-instance`: QA-пункт «два экземпляра» отмечен `[x]`, но блокировки нет — оба процесса читают-модифицируют-пишут JSON сцены (`with_scene`) и затирают друг друга.
- **Решение:** перед `runner().run()` копировать `red-companion.db` в `backups/` с номером схемы (хранить 3–5 копий); при ошибке открытия показывать нативный диалог с путём к файлу и логу; включить WAL и `busy_timeout`; подключить single-instance; кнопка «Резервная копия базы» (экспорт файла БД) — одна из функций доверия для 1.0.

### I2. Паника убивает приложение молча

- `Cargo.toml`: `panic = "abort"`, `strip = true`; логирования нет (нет `tauri-plugin-log`/`tracing`, нет hook'а паники). `expect(...)` на путях команд: `free_export_name` (lib.rs:596), `Collection::canonical_json` (`catalog.rs`, `expect("entries are serializable")`), плюс `unwrap` в тестах. Блокировка `Mutex` через `lock(&state)` возвращает ошибку (хорошо), но любая паника в команде завершает процесс без следа.
- **Решение:** `std::panic::set_hook` + лог-файл в `app_log_dir()`; заменить `expect` в путях команд на `Result`; в «О приложении» показывать путь к логам и версию.

### I3. Язык контента — глобальное состояние, гоняющееся между вызовами

- `src/lib/api.ts:65` `inLanguage`: сначала `invoke("set_content_lang")`, потом отдельный `invoke("list_*")`. Состояние — `Mutex<Lang>` (`ContentLang`). Два параллельных `inLanguage` с разными языками (переключение языка во время загрузки; хуки `use-reference-data`, `use-npc-templates` и др. грузят параллельно) перемешиваются: данные одного языка попадают в состояние другого.
- Для сети это станет хуже: кэш ключуется `(пакет, коллекция, язык)`.
- **Решение:** передавать `lang` параметром каждой команды (или `ContentLang` убрать совсем); команды, создающие NPC из шаблона (`create_npc_from_template`), тоже принимают язык явно.

### I4. Слой `DataSource` не готов к сети

- Трейт синхронный и возвращает владеющие `Collection<T>` (`data_source.rs`); `SeedDataSource` на **каждую** команду заново парсит вшитый JSON (`parse(include_str!(...))`, суммарно ~400 КБ seed). Для вшитого снимка это терпимо; для `ApiDataSource` нужен слой «прочитать из кэша без сети» плюс отдельный асинхронный шаг синхронизации.
- Команды Tauri без `async` выполняются в главном потоке (Tauri v2: «commands without `async` run on the main thread» — проверить в документации используемой версии); `make_portrait`, импорт и любая сетевая работа в таком виде будут подвешивать окно. Сетевые команды — только `async`, с `State<Arc<…>>`, а не `Mutex<Storage>` на весь вызов.
- `lib.rs` — один файл на 2432 строки (команды + тесты). Перед добавлением сетевых команд разнести на модули (`commands/characters.rs`, `commands/combat.rs`, `commands/net.rs`…).
- Устаревший комментарий `data_source.rs:78`: «Each language has its own server (`ru.…`, `en.…`)» — противоречит принятой модели (один сервер, `?lang=`).

### I5. Хэши и версии: клиент должен проверять сырой JSON

См. C1. Если клиент хэширует типизированную структуру, а сервер добавит поле (то, что `serde` без `deny_unknown_fields` молча отбросит), загруженная коллекция навсегда не пройдёт проверку. Решение — в «Несогласованностях».

### I6. Пользователям придёт чужой тип ошибок: `server.*` не переведены

- В `ru.json`/`en.json` нет ни одного ключа `errors.server.*`; `error_codes.rs` и `src-tauri/src/error.rs` не знают серверных кодов. Правило проекта (CLAUDE.md, раздел «Ошибки») требует перевода любого кода, который может дойти до UI, и тест `every_error_code_is_translated_in_both_languages`.
- Пользователь увидит «server.rate_limited» на фоне «Неизвестная ошибка». Приложению нужны (из `ApiErrorCode` сервера): `server.bad_language`, `unknown_collection`, `unknown_pack`, `unknown_release`, `invalid_request`, `unauthorized`, `revoked`, `rate_limited` (с `params.retry_after`), `unavailable`, `unknown_platform`. Остальные (`conflict`, `checksum_mismatch`, `invalid_signature`, `forbidden`, `unknown_app_release`) видит только CI.
- Режимы сети: «нет сети» — не ошибка, а тихое состояние (спецификация §11.4); ошибки показываются только при ручной проверке.

### I7. Сервер: «опциональные» настройки, дающие тихую неисправность в production

- `UPDATER_PUBLIC_KEY` пуст → подпись загружаемых пакетов не проверяется (`uploadAsset`, `verify`), в production это молчаливое отключение защиты. Должно быть обязательным при `NODE_ENV=production`.
- `publicOrigin()` (`app.ts`) при отсутствии `BETTER_AUTH_URL` подставляет `http://localhost:3000`: ссылки в ответе updater станут `http://localhost:3000/releases/...`. Нужен fail-fast при старте.
- `IP_HASH_SALT` отсутствует → ошибка не при старте, а на первом запросе регистрации.
- Подпись minisign проверяется только в режиме `ED` (prehashed, BLAKE2b-512); верность для реальных подписей `tauri signer` подтверждена только чтением (`minisign.ts`) — проверить на настоящем файле (checklist §6, п. 5).

### I8. Безопасность окна

- `tauri.conf.json`: `"csp": null`. Сегодня XSS-путей немного (React экранирует; `dangerouslySetInnerHTML` только для вшитых SVG в `card-board.tsx`; changelog на сайте выводится как текст через `whitespace-pre-line`), но после подключения сервера в UI попадут строки с чужого хоста (названия, описания, changelog, `donate_url`). Включить CSP (`default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; connect-src ipc: http://ipc.localhost` — сетевые запросы идут из Rust), оставить только нужные разрешения, проверять схему `donate_url` (сервер уже валидирует `http(s)`, клиент должен проверить ещё раз перед `openUrl`).
- Нет `minWidth/minHeight` окна (QA проверяла от 1100 px), иконка трея настроена, но обработчика нет (`trayIcon` в конфиге, ни `on_tray_icon_event`, ни меню в коде) — либо убрать, либо реализовать.

### I9. Подпись установщиков и доверие

- Первый релиз заведомо без платных сертификатов (решение 21). Windows: SmartScreen. **macOS:** сборка без подписи/нотаризации на arm64 после скачивания из браузера обычно «повреждена» и не открывается обходным способом (проверить на реальном Mac; это может изменить решение об объёме). Android: APK с сайта, разрешение на установку.
- `tauri.conf.json` без `bundle.publisher`, `copyright`, `category`, `shortDescription`; `src-tauri/Cargo.toml`: `authors = ["you"]`. NSIS по умолчанию на английском: для русскоязычной аудитории добавить `bundle.windows.nsis.languages` (проверить имя поля в схеме Tauri).

### I10. Конвейер проверок

- Приложение: `ci.yml` гоняет `cargo test` **только на Windows** и `npm run check/build` на Linux. Сборка под macOS (C-зависимость `webp`/libwebp) впервые произойдёт на теге, `fail-fast: true` в матрице релиза. После `cargo test` не проверяется, что `schemas/*.json`, `schemas/hash-vectors.json` и `src/bindings/*.ts` закоммичены в актуальном виде — а именно они уходят серверу как контракт.
- `release.yml`: задача `check` проверяет только версии и `CHANGELOG.md`, тесты и `npm run check` перед сборкой не запускаются; тег на непроверенном коммите опубликует релиз. Версия проверяется по `tauri.conf.json` и `package.json`, но не по `[workspace.package] version` в `Cargo.toml` (три места с `0.1.0`).
- Контракт: `contracts/.source.json` сервера указывает на коммит приложения `100e983`, текущий `HEAD` — `ba67269`. Содержимое `contracts/schemas` и `contracts/seed` сейчас **побайтно совпадает** с приложением (проверено `diff -r`), но штамп устарел; `contracts:check` не запускается ни в одном CI.
- Actions закреплены по тегам (`@v4`), не по SHA; секреты updater-ключа доступны всему шагу `npm run tauri build` (стандартный риск цепочки поставок: `npm ci` выполняет скрипты зависимостей).

### I11. Сервер: каждая мелочь, что ударит по пользователям

- **Лимит скачивания блокирует саму загрузку.** `getDownload` сначала `rateLimit(..., downloadsPerHour()=30, 3600)` — при превышении бросается 429 **до** редиректа. Предполагалось «не накручивать счётчик». Нужно: редирект всегда, счётчик — только пока лимит не исчерпан (общий NAT, университет, Telegram-превью).
- **`appBlock` берёт `min_supported` только из последнего релиза.** Выпуск без `RC_MIN_SUPPORTED` (переменная пуста по умолчанию) снимает обязательность обновления у всех. Правильно: максимум по всем видимым релизам.
- **Отзыв релиза ничего не откатывает.** `setRevoked` скрывает релиз из манифеста, updater и загрузок; у уже обновившихся остаётся отозванная версия, а откатиться некуда (updater даёт только `version > current`). Единственное исправление — новая более высокая версия; поэтому процедура «релиз сломан» должна быть описана и отрепетирована (hotfix `1.0.1` за 1 тег). Файлы отдаются с `Cache-Control: public, max-age=31536000, immutable` — отзыв не очистит кэши CDN/прокси, если они появятся.
- **`min_content_schema`/`max_content_schema`** есть в `AppRelease`, но CI их не отправляет и клиента с константой «максимальная понимаемая схема» нет; защита от «новый формат контента на старом приложении» сводится к ручному `min_app_version` при публикации (поле в админке есть, `PublishInput.minAppVersion`).
- **Ядро `import-seed` затирает правки админки** (см. C6).

### I12. Подмена/«откат» манифеста

Подписанный манифест не содержит времени выпуска и срока действия. Валидный старый манифест (от прокси, при ошибке кэша или злоумышленником на пути) приложение примет; `GET /releases/{n}/manifest` отдаёт старые подписанные манифесты намеренно. Клиент обязан хранить наибольший виденный `content.release` и отвергать меньший; серверу стоит добавить подписанные `issued_at` (в блок, подписываемый при каждом запросе) и ограничить допустимый возраст.

## Несогласованности с сервером

**C1. Где считается хэш: типизированная структура против сырого JSON (критично для 7.3/7.4).**
`Collection::content_hash` приложения (`catalog.rs`, `canonical_json`) хэширует `serde_json::to_value` от типизированных записей: поля `serde(default)` пишутся обратно, `Option::None` без `skip_serializing_if` становится `null`, неизвестные поля отбрасываются (в `rules-core` нет `deny_unknown_fields` — это хорошо для совместимости вперёд, но…). Сервер подгоняет под этот раунд-трип (`normalize.ts`, `withSchemaDefaults`: «the stored form is the one the app produces») и держит его тестом на seed. Проблемы:

1. Контрактный тест (`tests/contract-import.test.ts`) читает `readCollection` (живые опубликованные записи), а не путь выдачи API (`readReleaseCollection`) и не записи, созданные формой админки, — только импорт seed.
2. Добавленное сервером поле (например `image`, DLC-атрибут) у старого приложения отбрасывается при типизации; хэш по структуре не сойдётся с хэшем манифеста → коллекция навсегда «битая», хотя данные корректны.
3. `null` против пропуска: форма админки может сохранять пустые необязательные поля иначе, чем импорт seed.

**Решение:** клиент верифицирует `sha256(canonicalize(полученный JSON entries))` по манифесту (канонизация над `serde_json::Value`, а не над структурой), хранит в кэше сырой JSON и лишь затем разбирает в типы; функцию «канонизация Value» ввести в `rules-core` рядом с `canonical_json` и покрыть тем же `hash-vectors.json`. `withSchemaDefaults` на сервере остаётся для паритета seed, но перестаёт быть условием проверки. Добавить на сервере тест «запись, созданная через форму, отдаётся тем же JSON, что и вшитый эталон».

**C2. Формула `root` и `pack_meta`** — см. B5. Спецификация §5 и комментарий в `release.ts` расходятся с кодом.

**C3. Версия коллекции живёт в двух местах.** В приложении `Collection.version` — «bumped by hand» (`catalog.rs`), в seed: `armor`=2, `roles`=2, `shields`=2, остальные 1. Сервер при импорте берёт версию из ru-seed (`import-seed.ts`: `create: { version: ru.version }, update: {}`) и затем увеличивает при каждом релизе с изменившимся хэшем (`bumpVersions`). `needs_update` сначала сравнивает версию (`catalog.rs:716`): если вшитый снимок приложения будет собран с версией выше, чем у сервера, а содержимое разное, обновление **не** предложится; версия не входит в хэш и не привязана к релизу. Решение: решать «нужно ли обновлять» по хэшам из подписанного манифеста, `version` оставить информационным.

**C4. Плейсхолдеры и относительные URL в блоке `app`.** `update_url: "/api/v1/app/update/{target}/{arch}/{current_version}"` (одинарные скобки) против формата Tauri `{{target}}`, `{{arch}}`, `{{current_version}}`; `changelog_url` заканчивается на `?lang=`. Updater Tauri использует собственный `endpoints`, а не поле манифеста, так что поля — подсказка для кода приложения; описать формат в контракте или удалить.

**C5. Коды ошибок.** Спецификация приложения (§6) перечисляет 7 кодов, сервер реально использует 15 (`ApiErrorCode`). Приложению нужны перевод и поведение по каждому (I6). Особенно `server.rate_limited` (с `retry_after`) при регистрации.

**C6. Источник правды по контенту после запуска.** Спецификация (§12.3) обещает «экспорт релиза в формат `seed/`» и переход источника правды в базу. Такого скрипта нет, а `import-seed` перезаписывает **любую** запись, чьи `data`/`texts` отличаются от seed, и принудительно ставит `state: published` (воскрешает `retired` и черновики), создавая ревизию. Повторный `npm run contracts:sync` + `db:import-seed` после правок в админке сотрёт их (ревизия сохранится, но опубликованное изменится). Пакету `core` при импорте не создаются `PackText` — название и описание пакета в манифесте будут пустыми, пока их не заполнят в админке (`publish-checks.ts` проверок текстов пакета не содержит — проверить). Необходимо решение Q3 и защита (флаг «не трогать записи с правками в админке» либо запрет повторного импорта после первого релиза).

**C7. `fallback: true` из спецификации (§7.1) не выдаётся.** `assembleEntry` подставляет русский текст вместо пустого английского (`byLang[lang] || byLang.ru`) без отметки в ответе. Для приложения это невидимо; если нужна пометка «без перевода», её надо добавить в контракт и в схемы.

**C8. Токен установки без места хранения.** Спецификация предлагает SQLite приложения (или ключница ОС); в `crates/storage/migrations` таблицы нет. Нужна миграция V6 (токен, `installation_id`, последний виденный `content.release`, подпись манифеста для офлайн-проверки) и решение, шифровать ли токен (минимум — не писать в логи и экспорт).

**C9. Две копии `SERVER-SPEC.md`.** Копия в приложении (черновик №5, ссылки на Auth.js, `translations:write`, `POST /ci/app-releases`) и копия сервера (Better Auth, ручная загрузка переводов, `/api/ci/...` вне `/api/v1`, 15 кодов ошибок) расходятся в нескольких существенных местах (Auth.js → Better Auth, токен `translations:write` против ручной загрузки файла переводов, `POST /ci/app-releases` против `/api/ci/...` вне `/api/v1`, 7 кодов ошибок против 15). Источником правды стоит объявить копию сервера (она новее на S1–S10), в приложении оставить только ссылку; `tools/export-server-bundle.py` сейчас копирует устаревшую версию в обратную сторону.

**C10. Языки.** Сервер: `LANGUAGES = ["ru","en"]` и `languages` в манифесте как массив; приложение: `enum Lang { Ru, En }` (`Lang::from_code` отправляет всё неизвестное в `En`). Добавление третьего языка на сервере без выпуска приложения даст непредсказуемый результат. Манифест должен нести только языки, которые приложение заявило (`?lang=` сервер валидирует по своему списку).

**C11. `lang=all`.** Хэш выдачи `all-<sha256>` вычисляется «из ответа» и не входит в манифест — проверить подпись цепочкой нельзя; клиенту не использовать.

**C12. Авторизация и наблюдаемость.** Сервер использует `X-App-Version` из заголовка запроса (обновляет `Installation.app_version`); при регистрации принимает `app_version`, `os`, `lang` (≤32/64 символа, `os` свободная строка). Формат `os` не зафиксирован: договориться о значениях (`windows`/`macos`/`android` + версия).

1. **Q1. Объём 1.0.0.** Только Windows или также macOS/Android? ROADMAP 8.1–8.4 и 8.6 (`[ ]`: адаптив, Android-сборка, macOS-сборка, обновление APK) не выполнены; `release.yml` по умолчанию собирает Windows + два macOS-артефакта, Android включается флагом `ANDROID_ENABLED`. 6. **Q6. Публичный ли репозиторий приложения и можно ли публиковать данные по книге?** (B6; влияет на SignPath, лимиты Actions, видимость текстов.)
7. **Q7. Идентификатор приложения `app.red-companion`.** Для Android идентификатор станет именем пакета; дефис недопустим в Java-пакете — проверить, как его обработает Tauri (скорее всего заменит на `_`), и учесть, что после первой публикации поменять нельзя. Уже менялся дважды (`app.favoterm`, `com.user.red-companion`), миграция данных есть (`migrate_legacy_data`), но третьего переименования не должно быть.
8. **Q8. macOS без аккаунта Apple Developer.** Устроит ли «обход через настройки» (и работает ли он на актуальных версиях) или macOS переносится в 1.1 вместе с покупкой сертификатов? Доступна ли оплата Apple/сертификатов владельцу (spec §10.1, п. 4).
9. **Q9. Политика `min_supported`.** Кто и когда задаёт `RC_MIN_SUPPORTED`; что именно блокируется ниже минимума (только синхронизация с сервером или работа приложения; по спецификации локальный режим продолжает работать — подтвердить и показать в UI).
10. **Q10. Данные об установках.** Срок хранения `Installation` и `DownloadEvent`, чистка отозванных/неактивных, формат `os`, текст политики данных (IP хранится солёным хэшем — для российских пользователей уточнить юридическую квалификацию).
11. **Q11. Ссылки в листах на удалённые/выведенные записи.** Спецификация (§11.5) требует показывать «нет в базе» для кодов, которых нет в справочнике. В приложении сегодня все справочники вшиты; при подключении сервера (`retired`-записи, выведенные коды) это нужно реализовать и протестировать — как именно лист хранит `code` оружия/брони/шаблонов и что делает UI?
12. **Q12. Где хранится ключ updater и кто может тегировать релиз.** Ключ в секретах репозитория + сейфе владельца; на сервере `deploy`-ключ ограничен принудительной командой (хорошо). Нужна политика: окружение `production` с проверяющим есть только у сервера — в `Hex1s/red-companion` для тега релиза защиты нет (любой push тега с правом записи запускает публикацию). Использовать environment с обязательным подтверждением и `RC_CI_TOKEN`/updater-секреты привязать к нему.

## Приоритизированный план решений

Формат: **что** → *почему* → решение → усилия/риск → зависимость от сервера. Порядок внутри фазы — рекомендуемый. «Усилия»: S ≤ 0,5 дня, M 1–3 дня, L > 3 дней.

### Фаза P0 — до тега `v1.0.0` (иначе выпускать нельзя)

**P0-1. Решение по объёму и формальное закрытие вопросов Q1–Q4, Q6, Q8.** *Почему:* от них зависит всё остальное (платформы, сервер в 1.0 или 1.1, лицензия). Решение: собрать ответы (опросом), зафиксировать в ROADMAP; объявить серверную `SERVER-SPEC.md` источником правды. Усилия: S. Риск: низкий. Сервер: нет.

**P0-2. Updater: ключ, конфиг, плагин, разрешения, перезапуск.** *Почему:* B2, «дверь в одну сторону». Решение: `npx tauri signer generate` (владелец), `plugins.updater.pubkey` + `endpoints` (`https://red-companion.ru/api/v1/app/update/{{target}}/{{arch}}/{{current_version}}`), `tauri-plugin-updater` + `.plugin(...)` в `run()`, `updater:default` и `process:allow-restart` в capabilities, сборка проверки в Rust через `updater_builder()` для заголовка `X-App-Version` и запасного ключа, команды `check_update`/`install_update` с прогрессом событиями, секреты в GitHub, `UPDATER_PUBLIC_KEY` на сервере. Усилия: M. Риск: средний (подпись, NSIS-поведение, права записи в Program Files против per-user установки — проверить установочный режим). Сервер: P0-5 (анонимный эндпоинт), `UPDATER_PUBLIC_KEY` обязателен.

**P0-3. Регистрация установки и проверка манифеста.** *Почему:* B1, B5, I12. Решение: модуль `net` в Rust (async, `reqwest` с `rustls`), таблица `installation`/`manifest_state` (миграция V6), `register_installation` при первом запуске в фоне (отложенный повтор при 429/сети), `fetch_manifest` + проверка Ed25519 (`ed25519-dalek`) над канонизацией `Value`, монотонность `content.release`, статус для UI (`up_to_date` / `update_available` / `mandatory` / `offline`). Перевод всех `server.*` (I6). Усилия: L. Риск: средний (канонизация). Сервер: B5 (векторы подписи), I11 (`min_supported`), I12 (`issued_at`).

**P0-4. Экран «О приложении» и «Что нового».** *Почему:* без него пользователь не увидит update и changelog; решение 9 владельца. Решение: `GET /about?lang`, `GET /app/changelog?lang&since` с вшитым запасным текстом; версия из `app.getVersion()`; ссылка на донат через `openUrl` после проверки схемы. Усилия: M. Риск: низкий. Сервер: заполнить `Setting` в админке.

**P0-5. Исправления сервера, блокирующие надёжное обновление.** *Почему:* B3, I7, I11. Решение: (а) анонимный `GET /api/v1/app/update/...` с лимитом по хэшу IP; (б) `min_supported = max по видимым релизам`; (в) `getDownload` не бросает 429 до редиректа; (г) fail-fast при старте в production для `UPDATER_PUBLIC_KEY`, `BETTER_AUTH_URL`, `IP_HASH_SALT`; (д) тест-вектор подписи манифеста `contracts/manifest-vectors.json`, формула `root` в контракте; (е) целочисленные числа в zod-схемах (B5). Усилия: M. Риск: низкий. Зависит от нас: это работа в серверном репозитории.

**P0-6. Защита данных мастера (I1) и логирование (I2).** *Почему:* данные кампании невозвратимы. Решение: копия БД перед миграциями (3–5 ротируемых), WAL + `busy_timeout`, single-instance, нативный диалог при невозможности открыть БД, лог-файл + panic hook, `expect` → `Result`. Усилия: M. Риск: низкий. Сервер: нет.

**P0-7. Языковая гонка и CSP (I3, I8).** Решение: `lang` параметром команд; строгий CSP; `minWidth/minHeight`. Усилия: S–M. Риск: низкий (CSP проверить в `tauri dev`: шрифты и `data:`-портреты). Сервер: нет.

**P0-8. Репетиция полного релиза на живом VPS.** *Почему:* B4.
